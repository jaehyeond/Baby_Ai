# 비비 상시 운영과 2027년 2월 집 컴퓨터 이전

상태: 배포 전 조사·요구사항 정리. 서버 개설, 배포, DB 이전, 자동 활동 활성화는 아직 실행하지 않았다.

최신 방향(2026-09-11 사용자 추가 설명): 궁극적 목표는 비비를 하드웨어에 넣어 Physical AI의 뇌로 만드는 것이다. 외부 서버와 유료 AI API를 필수 전제로 삼지 않는다. 아래의 상시 장치는 소유한 별도 PC, 로봇 내부 컴퓨터, 선택적인 클라우드 서버 중 하나이며, 앞서 제안한 외부 Linux 서버는 가능한 임시 운영안으로 교정한다.

## 사용자 요구

1. 현재 PC를 꺼도 비비가 계속 활동해야 한다.
2. C드라이브의 부족한 용량을 고려해야 한다.
3. 2027년 2월부터 프로젝트와 비비를 집 컴퓨터로 옮길 수 있어야 한다.
4. 최종 실행 환경은 로봇 하드웨어다. 기억·경험·학습 상태를 함께 가져가고 외부 AI 서비스를 대체 가능한 구성요소로 둔다.

## 필수 조건과 선택 사항

- 활동하는 동안 전원과 연산 장치는 필수다. 개발 PC를 끄더라도 별도 장치가 켜져 있으면 된다. 모든 장치가 꺼져 있으면 계산은 멈추며, 저장한 상태에서 재개할 수 있다.
- 외부 임대 서버는 선택 사항이다. 소유한 별도 컴퓨터나 로봇 내부 컴퓨터가 실행 장치 역할을 할 수 있다. '서버'라는 프로그램 역할이 클라우드 임대를 의미하지 않는다.
- 외부 Gemini/OpenAI API 역시 최종 설계의 필수 조건은 아니다. 다만 현재 `conversation_handler.py`는 Gemini로 답변을 생성하고, 벡터 임베딩 경로는 OpenAI에 의존한다. 현재 코드를 그대로 두고 완전 오프라인 대화를 보장할 수 없다.
- FastAPI의 내부 API는 모듈 사이의 통신 인터페이스다. 한 장치 안에서도 실행할 수 있으며, 외부 유료 AI API와 구분한다.
- 로컬 모델로 바꾸는 것과 자기학습이 검증되는 것은 별개다. 로컬 LoRA 학습 코드는 있지만, 경험으로 배운 코어가 실제 행동을 개선하는 폐루프는 미검증이다. 기존 연구 제한과 `LOCAL_CORE_DISTILL=0`은 유지한다.

## 현재 확인한 사실

- 2026-09-11 조회에서 C 여유 약 2.46 GiB, D 약 1,581 GiB, E 약 1,037 GiB였다. 실행 시점별 값은 `preflight_2026-09-11.json`을 따른다.
- 프로젝트는 `E:/A2A/our-a2a-project`에 있다. 대시보드의 API 주소와 Neo4j 주소는 localhost다.
- Neo4j는 `2026.03.1 Enterprise`, 데이터베이스는 `neo4j`다. 경험 3,157개, 개념 1,122개, 관계 10,852개를 읽기 조회했다. 이 집계는 완전성 증명이나 백업이 아니다.
- Redis는 기존 Upstash 호스트의 DNS 조회가 실패했다. 계정의 보관 상태와 복원 가능한 백업은 확인하지 않았다.
- Docker CLI는 설치됐지만 Docker 엔진은 응답하지 않는다. 이미지 저장 위치는 확인하지 않았다.
- API lifespan에는 독립적인 주기 실행기가 없다. `/sleep` 페이지의 `MemoryConsolidationCard`가 사용하는 `useIdleSleep` 브라우저 훅이 30분 idle 뒤 기존 수면 작업을 호출한다. 해당 화면이 실행되지 않거나 브라우저·PC를 종료하면 이 타이머도 동작하지 않는다.
- `/api/curiosity`의 `explore_batch`는 실제 탐색 결과 없이 상태를 `learned`로 바꾸고 만족도를 고정한다. 이를 무인 학습 작업으로 운영하면 안 된다.
- 기존 memory replay는 그래프 가중치와 region mapping을 변경한다. 감정 중요도가 높은 과거 경험을 고르며 신규 경험에 한정하지 않으므로, 단순 주기 반복은 같은 기억을 계속 강화할 수 있다.
- `LOCAL_CORE_DISTILL`은 기존 연구 gate에 따라 OFF를 유지한다. 상시 가동은 모델 자기학습 검증과 별개다.

## 권장 배치와 순서

1. 비비 코어, 언어·인지 모델, 기억 저장소, 센서·행동 인터페이스를 대체 가능한 경계로 둔다. 최종 검증은 센서 관측 → 기억·예측·행동 선택 → 하드웨어 행동 → 외부 결과 관측 → 학습의 연결을 확인해야 한다.
2. 지금 24시간 가동이 필요하면 사용 가능한 별도 PC·소형 연산 장치를 먼저 확인한다. 장치가 없으면 임시 클라우드 운영과 장치 확보를 비교한다. 이 단계에서 임대나 구매를 필수로 확정하지 않는다.
3. 선택한 장치에 API, 저장소와 브라우저에 의존하지 않는 주기 실행기를 배치한다. 현재 PC가 꺼져도 활동이 계속돼야 한다는 요구는 유지하되, 외부 서버에 한정하지 않는다.
4. 하드웨어 이전을 위해 외부 모델 호출을 로컬 모델로 대체할 수 있게 하고 오프라인 동작 범위를 검증한다. 현재 Neo4j/Redis를 최종 임베디드 하드웨어에서도 그대로 사용할지는 실제 메모리·저장·지연 측정 후 결정한다.

현재 PC는 개발·접속·백업 보관 역할을 한다. 대형 빌드는 선택한 다른 장치에서 하거나 저장 위치를 E/D로 확인한 뒤 수행한다. C 여유가 부족한 현재 상태에서 Docker 이미지·GPU 모델을 새로 받지 않는다. 이식 가능한 실행 묶음과 파일 백업을 준비하며 특정 클라우드 업체의 전용 기능을 필수 의존성으로 추가하지 않는다.

집 컴퓨터로 프로젝트를 옮기는 것과 24시간 운영 위치를 옮기는 것은 따로 결정할 수 있다. 2027년 2월에는 개발 환경만 집으로 옮기고 상시 서버를 유지할 수 있다. 실행 환경도 집으로 옮기려면 집 컴퓨터 또는 별도 장치가 계속 켜져 있어야 한다.

## 이식 가능한 저장 계약

| 종류 | 내용 | 보관·이전 원칙 |
|---|---|---|
| 코드 | Git 프로젝트, Dockerfile, Compose, 실행 스크립트 | 저장소와 배포 묶음. 의존성·컨테이너 버전 고정 |
| 비밀 설정 | DB 암호, Gemini/OpenAI 키, 사용자 인증 설정 | 코드와 분리. 접근 제한한 설정 파일로 이전. 아카이브·로그에 자동 포함 금지 |
| 장기 기억 | Neo4j 노드, 관계, 속성, 인덱스, 제약조건 | 선택한 실행 장치의 영속 저장소 + 검증된 DB 백업. 비비 원본 보존 |
| 운영 상태 | 주기 실행 이력·잠금·마지막 처리 지점, Redis 영속 데이터 | 재시작 후 같은 작업을 중복 수행하지 않도록 영속화 |
| 학습 산출물 | 기존 로컬 adapter와 필요한 manifest | 코드와 별도 파일 자산. 정확한 경로·크기·해시를 인벤토리에 기록. CPU 서버에서 재학습하지 않음 |
| 백업 | DB 백업, 운영 상태, 버전·해시 manifest | 실행 장치와 별도로 E드라이브에 보관하고 집 PC로 이전 |
| 빌드·캐시 | Docker 이미지·레이어, pip/npm cache | 여유 공간을 확인한 장치·드라이브에서 생성. 집 PC에서는 넉넉한 드라이브 지정 후 재생성 |

E에 프로젝트나 데이터 폴더를 둔 것만으로 Docker 이미지가 E에 저장되는 것은 아니다. Windows Docker Desktop의 이미지 디스크 위치는 별도 설정이다. 현재 C 여유가 적으므로 로컬 이미지 pull/build는 하지 않는다. 가벼운 로컬 Python 확인은 기존 E의 `.venv`와 `-B`를 사용한다.

## 실제 활동 범위 결정

대화·조회 상시 대기는 기존 API 배포로 가능하지만, 무인 활동은 별도 실행기가 필요하다. 현재 후보는 신규 경험 유무 확인과 횟수를 제한한 기억 재생이다. 실행 시각·대상·실제 변경량·성공/실패를 기록하고, 중복 실행·재시작 후 재실행을 막는 계약이 필요하다. 실제 대상과 주기는 사용자 답변 후 확정한다.

기존 브라우저 수면 훅을 동시에 실행하면 이중 작업이 되므로 서버 실행기 전환 시 함께 조정한다. 기존 전체 감쇠·무제한 replay·상태만 바꾸는 탐색·GPU distill을 그대로 타이머에 연결하지 않는다. 아직 이 부분을 구현하거나 활성화하지 않았다.

## 데이터 이전 순서와 통과 조건

1. 상시 연산 장치, 접속 방법, 무인 활동 범위를 확정한다. 현재 모델 API를 사용하는 임시 운영과 로컬 모델까지 실행하는 구성을 구분해 필요한 메모리·연산량을 측정한다. 클라우드 임대나 장치 구매가 필요한 경우에만 그 예산을 결정한다.
2. 대상 Neo4j 버전·edition·store format을 정한다. 현재 Desktop Enterprise를 Community로 바꿀 때 단순 dump/load가 호환된다고 가정하지 않는다. 현재 실제 store format은 미확인이다.
3. 원본에 쓰기를 중단할 시간을 정하고, E에 일관된 백업과 manifest를 만든다. 원본 DB는 보존한다. 실행 중인 DB 디렉터리를 단순 복사하지 않는다.
4. 대상의 빈 DB에 복원한다. 라벨별 개수, 관계 유형별 개수, 속성·임베딩·애플리케이션 ID, 인덱스·제약조건을 대조한다. Neo4j 내부 ID는 동일하다고 가정하지 않는다.
5. 접근은 최초에는 SSH 터널 또는 사설 네트워크를 사용한다. 기존 API에 개인 기억 조회와 DB 변경 endpoint가 있으므로 인증 없이 공인 포트에 노출하지 않는다. 공개 웹 접속을 원하면 그 경로의 인증과 HTTPS를 별도로 완성한다.
6. 새 서버의 대화·기억 조회·Redis 알림·허용된 주기 작업을 확인한다. 재시작 후 데이터와 실행 이력이 유지되는지, 백업에서 다시 복원되는지 확인한다.
7. 새 서버를 유일한 쓰기 대상으로 바꾼다. 예전 PC와 새 서버가 갈라진 기억을 각각 갱신하는 상태를 피한다. cutover 후 rollback은 새 서버에서 생긴 경험까지 보존하는 절차가 필요하다.
8. 현재 PC가 꺼진 동안 독립된 장치에서 접속하고, 그 시간에 생성된 실행 기록을 확인한다. 이 검증 전에는 'PC 없이 상시 운영 완료'라고 보고하지 않는다.
9. 2027년 2월에는 동일 버전 묶음과 최신 백업으로 집 PC에 복원 리허설을 한 뒤 개발·실행 주소를 바꾼다. 기존 서버 종료는 복원 확인 뒤의 별도 단계다.

## 현재 필요한 입력

- 현재 PC 외에 켜 둘 수 있는 소유 장치가 있는지. 최종 로봇 형태와 탑재 컴퓨터의 제약은 실제 장치 선택 전에 확인한다.
- 외부 임대 서버·유료 API를 필수 조건으로 한 예산 질문은 철회한다. 클라우드를 선택하는 경우에만 그 비용을 결정한다.
- PC가 꺼진 동안 허용할 활동 범위.
- 집 PC로 개발 환경만 옮길지, 상시 실행 위치도 옮길지는 지금 확정할 필요가 없다. 두 경우를 모두 지원하는 구조로 준비한다.
